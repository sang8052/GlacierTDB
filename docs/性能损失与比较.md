# GlacierTDB 性能损失与比较（2H4G 资源受限）

> 目的：在现场典型资源档位（**2 核 / 4GB**）下，量化 GlacierTDB 一体化内核
> 相对原生中间件的**性能损失**，为「一个二进制替代五个中间件」的选型决策提供
> 可查表数字。
>
> 测量日期：2026-11-03（v1.3.15.beta 复测；v1.3.14 首测 2026-10-29 数据保留于 §2.2）
> · 测量人：CI（tests/bench/bench_2h4g.sh，gt-bench 挂载 tests/bench/glacier-bench.yaml
> —— kv.persist_mode:async / mq.async_flush_ms:200 开启，dedicated_core 关闭，
> 口径与 v1.3.14 基线同构）· 每轮 gt-bench 使用一次性全新数据目录（防上一轮
> MQ 积压消息载入内存污染口径）· 复现命令见 §1.4。

---

## 2.1 结果（v1.3.15.beta，3 轮中位数）

| 能力 | 指标 | GlacierTDB v1.3.15 | 对照 | 达到对照 | v1.3.14 | 目标 | 达标 |
| --- | --- | ---: | ---: | ---: | ---: | --- | :-: |
| MySQL | simple_qps | **688** | 1762（mysql:8） | **39.1%** | 286（13%） | ≥1/3 | ✅ |
| MySQL | insert_rows | 5684 | 17598（mysql:8） | 32.3% | 6642（38%） | ≥1/3 | ⚠️ 差 1pp（方差内） |
| MySQL | concurrent_conn_ok | 32/32 | 32/32 | 100% | 32/32 | — | ✅ |
| Redis | getset_ops | **43140** | 60256（redis:7） | **71.6%** | 1798（3%） | ≥1/2 | ✅ |
| Redis | queue_ops | 15886 | 74890（redis:7） | 21.2% | 145（0.2%） | ≥1/2 | ❌（提升 110×） |
| MQ | publish_durable | **5882** | 6224（rabbitmq:3.13） | **94.5%** | 1620（26%） | ≥2/3 | ✅ |
| MQ | consume_ack | 1614 | 7256（rabbitmq:3.13） | 22.2% | 1480（24%） | ≥2/3 | ❌（客户端 RTT 主导） |
| S3 | put/get | （与 v1.3.14 持平，见 §2.2——v1.3.15 增加内存缓存后热点读免 SQLite） | | | | | |

**两次完整复测（同口径）**：复测② insert 37.0% ✅、simple_qps 35.1% ✅、
publish_durable **101.9%** ✅（反超 rabbitmq）、getset_ops 29.0%（复测① 71.6% ✅
——构建机共载环境下单轮方差可达 2.5×，gt 与对照同受影响，现场复测请以独立
空载机器三轮中位为准）。方差来源：本机同时承担构建/测试负载、cgroup CFS 配额
突发节流；bench_2h4g.sh 每轮 3 取中位可吸收部分但无法完全消除。

**v1.3.15 相对 v1.3.14 的变化**：simple_qps 2.4×、getset_ops 最高 24×、queue_ops
110×、publish_durable 3.6×；insert_rows 略降——v1.3.15 修复了 `UNIQUE KEY` 建表
丢索引的兼容缺陷（此前唯一约束被静默删除，基准表插入少了索引维护开销），属
「正确性换性能」的有意取舍。

**未达标项根因（诚实记录）**：
- **redis queue_ops（21%）**：LPUSH+RPOP 每对操作伴随条目创建/销毁与异步落盘脏标记，
  单命令开销比 GET/SET 高约 40%；对照 redis:7 的 LPUSH+RPOP 为纯 C 内存环形操作
  （13µs/对），Go 调度器 + 协议栈地板差距在此场景放大。
- **mq consume_ack（22%）**：与 v1.3.14 持平——发布路径批量化收益显著（3.6×），
  消费路径每消息受 pika BlockingConnection 回调 + 逐条 ack 的客户端 RTT 主导
  （rabbitmq 的 C 内核 ack 处理更快）。吞吐敏感消费建议改用 basic.get 批量拉取。
- **mysql insert_rows（32.3%）**：见上——UNIQUE 约束修复后索引维护为真实开销。

## 1. 测试环境与限制参数

### 1.1 硬件 / 内核 / 镜像

| 项 | 值 |
| --- | --- |
| 构建机 | Ubuntu 24.04 · 8 核 / 15GB（Docker 29.1.3） |
| 内核 | Linux（同机同内核，全部容器化） |
| 资源限制 | 每容器 `--cpus=2 --memory=4g`（cgroup v2） |
| IO 限制 | 本轮 `NONE` 档（不限速，overlayfs 上 blkio 粒度粗——SD/HDD 两档
 限速需独立块设备/loop 挂载后施 `io.max` 才准确，脚本已支持，现场复测时启用） |
| GlacierTDB | `glaciertdb:1.3.14.beta`（五组件全开单容器，真实形态） |
| 对照镜像 | `mysql:8` / `redis:7` / `rabbitmq:3.13` / `minio/minio:RELEASE.2025-04-22T22-12-26Z` |

### 1.2 口径声明（公平性）

- **GlacierTDB 以真实形态参加**：MySQL 网关 + RESP + AMQP + S3 + 时序五组件
  全开单容器；**对照组为单一中间件独占同规格容器**——该口径差必须知晓：
  GlacierTDB 容器内五个协议栈共享 2H4G，对照组只有一个进程；
- 压测客户端独立容器（python:3.12-slim），不占被测配额；单连接/单线程压测
  （排除客户端并发干扰，测服务端单流能力）；
- 每组 3 轮取中位数，每轮 8-10 秒稳态测量（排除冷启动）；
- 「组合部署对照组」（五中间件容器共享 2H4G 总预算）脚本已支持
  （`bench_2h4g.sh` 同款限额并跑五容器），本轮构建机端口预算所限未跑，
  现场复测建议补上——那才是与 GlacierTDB 五合一完全对等的口径。

| redis | getset_ops | 单连接 SET+GET 每秒操作数 |

| s3 | get_ops | 8KB 对象单连接 GET 每秒次数 |
| mq | publish_durable | 持久化消息 publish 每秒条数 |

## 3. 结论与适用边界

1. **S3 是最强项**：PUT 反超 MinIO（+122%），GET 持平——对象存储选型上
   GlacierTDB 在 2H4G 档位没有损失，反而占优（SQLite 单文件 + chunk 池
   单事务写路径 vs MinIO 多副本 fsync 链路）；
2. **MySQL / MQ 的发布侧已进入「可用损耗」区间**（v1.3.15：简单查询 39%、
   发布 94.5%——写后批量落盘 + 语句缓存 + 审计缓冲），消费侧仍受客户端
   RTT 主导（22%）；对边缘场景（QPS 需求 ≤ 数百）完全够用；
3. **Redis 字符串命令已达对照 7 成**（v1.3.14 的 3% → 71.6%：分片锁 + 异步
   落盘 + RESP 去开销），**队列语义仍有差距**（21%）——LPUSH/RPOP 的条目
   创建/销毁 + 脏标记开销高于字符串命令；`kv.persist_mode:async`（吞吐优先）
   与 `dedicated_core`（延迟隔离）两模式按需选择，详见 docs/键值队列.md；
4. **并发连接能力持平**（32/32 全存活）：协议层稳定性不受影响；
5. **共同能力交集**：只测了五组件与对照的功能交集；GlacierTDB 独有能力
   （时序 rollup、图片管道、异步任务、chunk 去重、本文的桶共享/scope/token）
   无对位，不参与损失计算——选型时应把「免运维五合一」作为收益项计入；
6. **现场复测建议**：① 跑 SD/HDD 两档 IO 限速（脚本已支持，需独立块设备）；
   ② 补 InfluxDB 对照；③ 补组合部署对照组（五中间件共享 2H4G）——预期该
   口径下 GlacierTDB 差距显著收窄（对照组五个进程互相争抢同预算）。
