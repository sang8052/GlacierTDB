# GlacierTDB 性能损失与比较（2H4G 资源受限）

> v1.3.14 需求 §5 交付物。目的：在现场典型资源档位（**2 核 / 4GB**）下，量化
> GlacierTDB 一体化内核相对原生中间件的**性能损失**，为「一个二进制替代五个
> 中间件」的选型决策提供可查表数字。
>
> 测量日期：2026-10-29 · 测量人：CI（tests/bench/bench_2h4g.sh）· 复现命令见 §1.4。

## 1. 测试环境与限制参数

### 1.1 硬件 / 内核 / 镜像

| 项 | 值 |
| --- | --- |
| 构建机 | Ubuntu 24.04 · 8 核 / 15GB（Docker 29.1.3） |
| 内核 | Linux（同机同内核，全部容器化） |
| 资源限制 | 每容器 `--cpus=2 --memory=4g`（cgroup v2） |
| IO 限制 | 本轮 `NONE` 档（不限速，overlayfs 上 blkio 粒度粗——SD/HDD 两档
 限速需独立块设备/loop 挂载后施 `io.max` 才准确，脚本已支持，现场复测时启用） |
| GlacierTDB | `glaciertdb:1.3.14.beta`（五组件全开单容器，真实形态） |
| 对照镜像 | `mysql:8` / `redis:7` / `rabbitmq:3.13` / `minio/minio:RELEASE.2025-04-22T22-12-26Z` |

### 1.2 口径声明（公平性）

- **GlacierTDB 以真实形态参加**：MySQL 网关 + RESP + AMQP + S3 + 时序五组件
  全开单容器；**对照组为单一中间件独占同规格容器**——该口径差必须知晓：
  GlacierTDB 容器内五个协议栈共享 2H4G，对照组只有一个进程；
- 压测客户端独立容器（python:3.12-slim），不占被测配额；单连接/单线程压测
  （排除客户端并发干扰，测服务端单流能力）；
- 每组 3 轮取中位数，每轮 8-10 秒稳态测量（排除冷启动）；
- 「组合部署对照组」（五中间件容器共享 2H4G 总预算）脚本已支持
  （`bench_2h4g.sh` 同款限额并跑五容器），本轮构建机端口预算所限未跑，
  现场复测建议补上——那才是与 GlacierTDB 五合一完全对等的口径。

| mysql | insert_rows | 500 行/批 INSERT 每秒行数 |

| s3 | put_ops | 8KB 对象单连接 PUT 每秒次数 |
| s3 | get_ops | 8KB 对象单连接 GET 每秒次数 |
| mq | publish_durable | 持久化消息 publish 每秒条数 |
| mq | consume_ack | consume+ack 每秒条数 |

## 2. 结果（3 轮中位数）

| 能力 | 指标 | GlacierTDB | 对照 | 损失（对照为基准） |
| --- | --- | ---: | ---: | ---: |
| MySQL | simple_qps | 286 | **2244**（mysql:8） | -87%（约 7.8×慢） |
| MySQL | insert_rows | 6642 | **17297**（mysql:8） | -62%（约 2.6×慢） |
| MySQL | concurrent_conn_ok | 32/32 | 32/32 | 持平（全部存活） |
| Redis | getset_ops | 1798 | **58213**（redis:7） | -97%（约 32×慢） |
| Redis | queue_ops | 145 | **76622**（redis:7） | -99.8%（约 528×慢） |
| TSDB | write_rows | 5532 | （influxdb:2 本轮未纳入） | — |
| TSDB | range_agg_qps | 12.5 | （同上） | — |
| S3 | put_ops | 160 | **72**（minio） | **+122%（快 2.2×）** |
| S3 | get_ops | 279 | **304**（minio） | -8%（基本持平） |
| MQ | publish_durable | 1620 | **6298**（rabbitmq:3.13） | -74%（约 3.9×慢） |
| MQ | consume_ack | 1480 | **6251**（rabbitmq:3.13） | -76%（约 4.2×慢） |

> 脚本路径 `bench_all.py tsdb --tsdb-url ...` 已就绪；TSDB 行按 raw SQL 语义
> 测（points 表 = 时序大表声明 + rollup 路由），与 Influx line protocol 的
> 写放大差异大，现场复测时两口径都要跑并注明。

## 3. 结论与适用边界

1. **S3 是最强项**：PUT 反超 MinIO（+122%），GET 持平——对象存储选型上
   GlacierTDB 在 2H4G 档位没有损失，反而占优（SQLite 单文件 + chunk 池
   单事务写路径 vs MinIO 多副本 fsync 链路）；
2. **MySQL / MQ 属「重协议网关」量级**：简单查询慢约 8×、持久化消息慢约 4×
   ——根因是每个请求都要走 MySQL/AMQP 协议解析 → SQLite 事务落盘全链路
   （对照组是纯内存引擎路径为主）。对边缘场景（QPS 需求 ≤ 数百）完全够用；
   高频小查询场景请评估 `per_db_read_threads` 与 QoS 配置后实测；
3. **Redis 是最大差距项**（单连接 ops 慢 1-2 个数量级）：RESP 命令逐条走
   3309 多路复用 + KV 落盘（AOF 语义），而 redis:7 是内存态。**队列语义差距
   最大（528×）**——LPUSH/RPOP 每次操作都持久化。适合做缓存伴随存储与
   低频队列，不适合替代高吞吐 Redis 集群；
4. **并发连接能力持平**（32/32 全存活）：协议层稳定性不受影响；
5. **共同能力交集**：只测了五组件与对照的功能交集；GlacierTDB 独有能力
   （时序 rollup、图片管道、异步任务、chunk 去重、本文的桶共享/scope/token）
   无对位，不参与损失计算——选型时应把「免运维五合一」作为收益项计入；
6. **现场复测建议**：① 跑 SD/HDD 两档 IO 限速（脚本已支持，需独立块设备）；
   ② 补 InfluxDB 对照；③ 补组合部署对照组（五中间件共享 2H4G）——预期该
   口径下 GlacierTDB 差距显著收窄（对照组五个进程互相争抢同预算）。
