# GlacierTDB 异步查询路线（后续规划）

> 状态：**设计稿，未实现**。为**超大数据查询**（百万行级导出、全表聚合、时序长范围回算）提供异步执行模型：
> 提交秒回 job_id，结果就绪后 **HTTP 回调**通知，或客户端用 **SQL 主动拉取**。
> 延续红线：纯 Go、零中间件、结果落盘不占内存。

---

## 1. 模型

```
客户端                        GlacierTDB                         回调目标
  │ SUBMIT QUERY '...'            │                                 │
  │   [CALLBACK 'http://cb']  ──► │ 校验 → 入队 → 返回 job_id（秒回）│
  │                                │ worker 池执行（受 global_threads 闸门）
  │                                │ 结果流式物化 → db_dir/jobs/<id>.jsonl
  │                                │ ── 完成通知（带 HMAC 签名头）────► │
  │ SELECT * FROM query_jobs       │                                 │
  │ FETCH QUERY RESULT <id> …  ◄── │ 分页拉取（LIMIT/OFFSET 流式读）  │
```

三种消费方式自由组合：**回调推送**（适合服务间）、**SQL 拉取**（适合人/脚本）、**混合**（回调通知 + 按需拉数据）。

## 2. 提交与消费（私有 SQL）

```sql
-- 提交（秒回 job_id）
SUBMIT QUERY 'SELECT series_id, count(*) FROM points GROUP BY 1'
       [CALLBACK 'http://ops.internal/hook']
       [TIMEOUT 3600];                       -- 秒，默认 1800

-- 主动查询状态（也支持表形式）
SHOW QUERY JOBS;
SELECT * FROM query_jobs WHERE status = 'RUNNING';
-- 列：job_id / state(PENDING|RUNNING|DONE|ERROR|CANCELLED|EXPIRED)
--     / sql / submit_ts / start_ts / elapsed_ms / rows / bytes / error / callback_url

-- 拉取结果（两种等价写法；流式分页读，不整体载入）
FETCH QUERY RESULT 'j_20261015_000123' LIMIT 1000 OFFSET 5000;
SELECT * FROM query_result('j_20261015_000123') LIMIT 1000 OFFSET 5000;

-- 取消 / 清理
CANCEL QUERY 'j_20261015_000123';
DROP QUERY RESULT 'j_20261015_000123';       -- 提前释放磁盘
```

## 3. HTTP 回调

完成（或失败）后向 `CALLBACK` 地址 `POST` JSON：

```json
{ "job_id": "j_20261015_000123", "state": "DONE",
  "rows": 8640000, "bytes": 412888123, "elapsed_ms": 18422,
  "result_sha256": "…", "expires_ts": "2026-10-16 00:12:03",
  "error": null }
```

- 数据本体不进回调（可超大），回调只给**元信息 + 拉取凭证**；小结果（≤64KB）可内联 `data_base64`；
- 防伪：请求头 `X-Glacier-Signature: sha256=HMAC(<提交时返回的 secret>, body)`；
- 交付语义：`2xx` 视为成功；失败退避重试 3 次（1s/10s/60s）；重试与最终状态在 `query_jobs.error`/日志可查。

## 4. 存储与生命周期

| 项 | 设计 |
| --- | --- |
| 结果文件 | `db_dir/jobs/<job_id>.jsonl`（JSON Lines，流式写/流式分页读）；`max_result_rows` 对异步放宽为 `async_max_result_rows`（默认 1 亿，磁盘为界） |
| 元数据 | `query_jobs` 表（内置库，复用每库写锁模型） |
| TTL | 结果保留期可配（默认 24h，到期 EXPIRED 后物理删除） |
| 磁盘水位 | `jobs_dir` 可配上限（占用超限拒绝新提交，报 507 语义错误） |
| 并发 | 异步 worker 池（配置 `async_workers`）；与在线查询共享 `global_threads` 闸门，防后台大查询饿死在线业务 |
| 取消 | `CANCEL` 置位 → 执行中的 SQLite interrupt → 状态 CANCELLED，删半成品文件 |
| 管理 | 管理面 `SHOW QUERY JOBS` 全局可见；`KILL` 语义复用 |

## 5. 配置（规划）

```yaml
async_query:
  enable: true
  workers: 2                # 并发执行数
  max_result_rows: 100000000
  result_ttl_hours: 24
  jobs_dir: ""              # 默认 <db_dir>/jobs
  jobs_dir_max_gb: 0        # 0=不限
  default_timeout_sec: 1800
  callback_max_inline_kb: 64
```

## 6. 典型场景

- **百万行导出**：BI 工具提交 → 回调通知 → 服务端按 10 万页拉取转 CSV；
- **时序回算**：夜间提交全聚合 → 晨间 `query_result` 取回；
- **慢查询不占连接**：提交后连接即释放，避免网关连接被长查询钉死。

## 7. 明确不做

- ✗ 长轮询/SSE 流式推送连接（回调 + 拉取已覆盖；保持网关无状态连接）；
- ✗ 跨实例任务调度——单机模型（与现有一致）。
